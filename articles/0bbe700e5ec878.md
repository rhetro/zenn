Rustのコンパイラによって厳しく制限されている「複数要素への同時可変参照」を突破した`Ordex`をベースとして動くものを作成しようと思い、最初に思いついたのが非線形構造の定番のPrey & Predatorの実装でした。

Lotka-Volterraモデルと呼ばれるこの非線形モデルは、Prey（被捕食者）とPredator（捕食者）の個体数の変化の関係を、２つの非線形常微分方程式で表したものです。

$$
\begin{aligned}
\text{Preyの増加：} \quad &\frac{dx}{dt} = ax - bxy \\
\text{Predatorの増加：} \quad &\frac{dy}{dt} = cxy - dy
\end{aligned}
$$
（$a, b, c, d$ は正の定数）

エサであるPreyが増えればPredatorが増え、エサであるPreyが減ればPredatorも減少していく。
そして、Predatorが減少すれば、再びエサであったPreyが増えそれに追随するようにPredatorも増えていく。

という周期的な循環構造を数式でモデル化したものです。

今回は、このマクロな数理モデルを、ミクロな個体群のシミュレーションである「Boids（群れアルゴリズム）」と融合させました。

画面上を飛び回る数千のPreyとPredatorが、それぞれ自律的に群れを形成し、逃げ、捕食し合うことで、全体としてLotka-Volterraの増減サイクルを描き出します。（Preyは意図的に不可視化してあります。）

このPreyとPredatorは、相互に作用しているため、プログラム上では、常にメモリポインタの参照元が入れ替わっていくところに、実装の複雑性が生じます。

Ordexをこのベースにおくことで、非線形構造の最も複雑なランタイム処理をすべて事前検証済みのものとして安全に扱うことが可能になり、Web Assemblyとしてコンパイルしても、そのパフォーマンスがバイナリ上で維持され、実行環境では、ハードウェアの限界値に張り付くスコアを出しています。

- [GitHub Repository](https://rhetro.pages.dev/rust/ordex/)

## 1. 空間ハッシュの真の役割 ― 動的グラフのトポロジー変換

Boidsモデルにおいて、各ノードは自身の次状態を決定するために「周囲一定半径の全ノードの状態」を同時に参照しますが、これはデータ構造の視点から見れば、毎フレーム接続の形が変動し続ける巨大な動的グラフ（ネットワーク）に他なりません。

通常、この計算量（`O(N^2)`）を削減するために「空間ハッシュ（Grid Cells）」という、シミュレーション空間を一定サイズのグリッドに分割し、各エンティティが属するセルを毎フレーム振り分ける手法が用いられますが、Ordexの文脈においてこれは単なるアルゴリズムの最適化ではなく、無秩序に絡み合う非線形な参照関係（時間的な動的グラフ）をセルのインデックスという「決定論的で素（Disjoint）な空間構造」へと写像し、固定化するための準備段階として機能しています。

この空間トポロジーへのマッピングが完了して初めて、Ordexによるエイリアシングの決定論的な空間検証が可能になります。

## 2. Ordexの適用 ― 非線形相互作用の空間的還元

従来のRustでは、こうした動的ネットワークの更新に `Rc<RefCell<T>>` 等を用いた時間的な状態監視を各ノードに挟み込む必要がありましたが、今回の実装ではOrdexによる静的および動的な空間トポロジーへの射影を用いることで、この時間的調停を完全に排除しています。

### ① 局所的特異点における静的アライメント（捕食フェーズ）
PredatorがPreyを捕食する特異点において、システムは「Predatorのエネルギー増加」と「Preyの非アクティブ化」を同期的に処理する必要があるため、対象が2要素に特定されているこの場面ではマクロによる静的トポロジーへの射影（`align!`）を適用します。

```rust
// predator_idx と prey_idx が重複していないことをレジスタ上で確定
align!(self.arena, pred_idx, prey_idx, |pred, prey| {
    prey.is_alive = false;
    pred.energy += cfg.pred_heal_amount;
});
```
動的なロック状態を一切生成せず、CPUのアウトオブオーダー実行（遅延隠蔽）に吸収される数ナノ秒の静的検証のみで、空間的な非重複性を担保したまま状態更新が完了します。

### ② バケットルーティングによる動的空間の再構築（群行動フェーズ）
Boidsの群れルールの適用フェーズでは、空間ハッシュによって分割された「あるセルに属する不特定多数のエンティティ」に対する一括の可変アクセスが発生するため、インデックス集合が動的に変動するこの領域には `ordex` によるバケットルーティングを適用します。

```rust
// 空間ハッシュから取得したインデックス群を非重複空間へバッチ変換
self.batch_buffer.clear_and_verify(&self.prey_neighbors_buf);

// 時間的ロックなしに、安全なイテレータとして空間全域を更新
self.arena.ordex(&self.batch_buffer, |mut iter| {
    while let Some(boid) = iter.next() {
        // 近傍ノードからの影響計算と速度更新
    }
});
```
不連続なアクセスであっても`clear_and_verify`を用いて内部のワークスペース（SoA配置バッファ）を循環利用することで、Ordexのエイリアシング検証（`align!` / `ordex`）自体は完全なゼロアロケーションで動作します。

もちろんアリーナ自体は内部で`Vec`を使用しているため新規要素の追加時には通常のアロケーションが発生し得ますが、今回のBoids実装ではメインループ内の処理をすべて事前確保バッファへ移譲することで最も負荷の高い計算フェーズの完全なゼロアロケーション化を達成しており、非線形な相互作用が償却`O(N)`の直列的な空間処理へと還元されています。

## 3. WASMバイナリへの純粋還元と実行パフォーマンス

Ordexによって計算フェーズの実行時監視とヒープ割り当てを排除したことで、WASM環境において計算側が律速になる可能性はほぼなく、javascriptによる描画側の負荷が支配的になります。

3,500体規模のBoidsを`Rc<RefCell<T>>`等を用いた旧来の動的借用で実装した場合、WASM環境でのFPSは15〜30程度まで低下すると考えられます。

アクセスごとの借用状態のチェックやパニック判定の分岐がループ内に挟まることでオーバーヘッドが増大し、LLVMによる自動ベクトル化などの最適化が阻害されるためです。

Ordexを用いた今回の実装には、この実行時の状態監視が存在しません。計算フェーズのヒープ割り当てを排除し、メモリ空間上の安全性をトポロジーの配置として事前に証明したことで、コンパイラは純粋な計算命令としてWASMバイナリを展開します。

また今回は視覚的な理由からPreyの描画を一部不可視化していますが、結果としてこれがWASM最大のボトルネックであるJS（Canvas API）へのコール負荷を低減させています。

描画側の律速が支配的になるため、計算フェーズの性能はディスプレイのVSync上限を十分に上回ることが期待されますが、実際に上限へ張り付くかどうかは環境依存であり、今回はそこまでの検証は行っていません。

## 4. 非線形システムの基盤としてのOrdex

この実装では、単なるBoidsの実装ではなく、非線形システムのランタイム処理を実行時のロック（時間）ではなく事前検証済みのトポロジー空間へと還元することで、Rustの厳格な安全性を維持したままハードウェアの物理限界に到達できることをOrdexで証明するものです。

Rustでの非線形システムの実装が困難な理由は、状態の衝突をランタイム時の監視で防ごうとするためです。

Ordexは、この動的な処理の前提を、予め検証済みのトポロジー空間へと再配置することで計算モデルを再定義し、GUI、ECS、動的ネットワークといった非線形システムをハードウェアの速度で動作させる基盤となります。
