## 1. Rustの構造的制約と計算モデルの再解釈

2025年末に**Cognitive OS**という非LLM型AIのアーキテクチャを着想し、2026年にその概要の論文をZenodoに発表しました。研究機関には所属はしておらず、Rhetroという名前で個人で開発しています。

**Cognitive OS**を実装していく中で、Rustがかかえるいくつかの構造的制約に扱いづらさを覚えたため、それを解決するCrateをGithubやCrates.ioに公開しています。

### 自作Crate群のスコア／ベンチマーク（一部）

- 100M要素を８コアで、687msでソート（[zan-sort](https://github.com/rhetro/zan-sort)）
- 1.36GB/sのProtobufルーター（[axiomabuf](https://github.com/rhetro/axiomabuf)）
- ASTやproc-macroを使わず、macro_rules!（宣言的マクロ）のみでDSLを構築（[Opejson](https://github.com/rhetro/opejson)など）
- Rustのborrow checkerを構造的に突破するaliasingモデルのArena Allocator（[Ordex](https://github.com/rhetro/ordex)）
など

上記のスコアやベンチマークは、新しいアルゴリズムを発見したり特殊なハックを行ったわけではなく、計算の構造を再構築することで実現しました。

Rustだったからこそ安全性を保ったまま構造の再定義を行えた部分はありますが、そもそもの発想は、Rustという言語に依存してるわけではなく、計算自体の構造的再解釈です。

そして、これらはRustの安全性の文化を破壊するものでもなければ、既存の方法論を否定するものではありません。
まったく新しい別軸のアプローチとして成立しています。

実装パターンや方法論ではなく、そもそも何がボトルネックやオーバーヘッドの原因になっているかを考え、それをどう回避するかということを徹底しています。

これらのツール群は、個別の最適化ではなく、動的計算を構造や静的トポロジーで解決しようとする試みです。


## 2.動的計算を構造で消すという発想

動的計算は、構造とトポロジーの設計によって静的化できます。

プログラミング言語における従来の計算モデルは、階層構造の探索、実行時の同期、比較評価、所有権の動的検証といった「動的計算（Dynamic Computation）」を必須のランタイムコストとして扱ってきました。

しかし、これらは問題を事前に決定された構造（トポロジー）と座標空間へマッピングすることにより、コンパイル時あるいは実行前の段階で計算そのものを消去することが可能になります。

### 動的トラバーサルから静的ポインタチェーンへ

RustにおいてJSONは通常serdeというクレートを用いてStructにデシリアライズして扱いますが、Opejson, Xopsy, Axiomaなどのクレートでは、そもそもパースすることをやめ、JSONをそのまま静的空間へマッピングします。

そうすることで、文字列パスの動的解析やポインタ追跡に伴う探索オーバーヘッドはそもそも発生せず、コンパイル時にネイティブなメモリへの直接アクセス命令と固定ポインタチェーンへ事前展開されるため、探索という計算そのものが発生しません。

### 同期・借用調停からトポロジー的分離（Disjoint）証明へ

実行時にロックや借用チェッカーが行う安全性の保証は、実行時の検証ではなく、事前検証としてコンパイル時に数学的に証明できるため、ランタイムでの検証・同期計算が不要になります。（Ordex、Ordagなど）

### 実行幾何（Execution Geometry）による事前計算

Sortingは通常、比較評価（Ord）により要素同士を動的に比較し、その結果に基づいて順序を決定します。

しかし、この「比較」という処理そのものが動的計算のオーバーヘッドであり、データ量に比例してランタイムコストとして蓄積していきます。

Zan-sortでは、このランタイム時の比較評価（Ord）を完全に捨てて、順序付けを「メモリ帯域の飽和問題」として扱いました。全ての要素を単一の`u64`キーに還元し、キー空間を静的な構造として扱うことで、順序付けは「事前に決定された書き込みトポロジー」を満たすだけの静的な幾何操作として実行されます。

この構造では、「比較」というランタイムコストは一切発生せず、ソート処理そのものが「静的に決定された幾何構造の適用」へと変換されます。

このように、さまざまな動的処理を空間・トポロジーの決定論的構造へ落とし込む設計に変換することで、不要なランタイムコストやオーバーヘッドを解消していくことが可能になります。


## 3. macro_rules!で構造をそのまま計算する

動的構造計算は、純粋な`macro_rules!`のみで構築することができます。

一般的に、コンパイル時計算やDSLの構築は、`proc-macro`や`syn`/`quote`といったAST生成ライブラリに依存します。しかし、これらはコンパイル時間の増大、中間生成物のオーバーヘッド、そして「構造を構造として扱う」ことが難しくなるという問題点を抱えています。

自作のCrate群では、こうした外部依存をすべて排除し、Rust標準の宣言的マクロ`macro_rules!`のみを使って構造計算を完結させています。これは単なる「軽量化」ではなく、トークンストリームそのものを構造空間として扱うという設計思想に基づいています。

### Raw Token Streamを構造空間として扱う
`macro_rules!`は、ASTではなく「生のトークン列」を扱います。そのため、「型」を扱えないなどのデメリットがあり、通常は簡易的なスニペットとして使われることが多いと思います。一方で、このトークン列を構造空間として扱うと、型構築・トポロジー投影・パスルーティングを中間生成物無しで1-passで展開することができます。

Axioma、Axiomabuf、EmlexなどのCrateは、この「トークン空間で構造を直接計算する」という手法により、コンパイル時に座標空間やジャンプテーブルを作成します。

### CPS（継続渡しスタイル）による構造計算の拡張
宣言的マクロは再帰に弱いという制約があります。これを回避するために、CPS（Continuation-Passing Style）という手法を導入し、深いネストや複雑な構造評価を安全に展開できるようにしました。

EmlexのS式パーサやXopsyの構造探索は、このCPS展開によって「宣言的マクロのみで構造計算を行う」という領域を広げています。

### コンパイル時座標空間への投影

JSONやS式などの階層構造は、前述ように通常はランタイムでパースされ、ヒープ構造（Vec, Hashmap）として扱われます。

しかし、AxiomaやOpejsonでは、これらをコンパイル時に２次元座標空間や静的ポインタチェーンへ投影します。

その結果、ランタイムでのパース処理やヒープ割り当ては完全に消滅し、構造は「静的に決定された座標空間」として扱われるため、探索も非常に高速になります。

このように、`macro_rules!`を「構造計算機」として扱う方法論は、外部エコシステムに依存することなく、Rustの基本機能だけで静的構造計算のパラダイムが成立することを示しています。


## 4. Crate群に投影された構造モデル

これらのCrateは、個別のユーティリティや最適化テクニックの寄せ集めではなく、構築された各ツールがすべて同じ構造原理を異なる領域へ投影したものです。

これらは、はじめに述べた「動的計算の構造的消去」という原理を、実際の計算領域へ適用した結果として生まれた具体的なツールです。

それぞれが扱うドメインは異なりますが、内部で成立してる計算モデルはすべて同じ構造的発想に基づいています。

### Execution Primitives（[Zan-sort](https://github.com/rhetro/zan-sort) / [Ordex](https://github.com/rhetro/ordex) / [Ordag](https://github.com/rhetro/ordag) / [Ordent](https://github.com/rhetro/ordent)）

Zan-sort、Ordex、Ordag、Ordentといった実行基盤系のCrateは、ランタイムで発生する比較・同期・借用調停・位相同期といった動的計算を、静的な幾何構造やトポロジーへ置換するためのエンジンとして機能します。

ソート、アリーナ、DAG、同期といった異なる領域でありながら、どれも「動的処理を静的構造へ落とし込む」という同じ原理で成立しています。

### Static Projection（[Axioma](https://github.com/rhetro/axioma) / [Axiomabuf](https://github.com/rhetro/axiomabuf) / [Emlex](https://github.com/rhetro/emlex)）

Axioma, Axiomabuf, Emlexは、JSON、Protobuf、S式といった階層構造を持つデータを、コンパイル時に座標空間やジャンプテーブルへマッピングするためのツールです。

これらは「ランタイムでパースする」という前提そのものを捨て、構造を静的に決定することで、動的計算を物理的に消去します。

### Dynamic Surgery（[Opejson](https://github.com/rhetro/opejson) / [Xopsy](https://github.com/rhetro/xopsy) / [Opeyml](https://github.com/rhetro/opeyml) / [Xopsyml](https://github.com/rhetro/xopsyml)）

Opejson、Xopsy, Opeyml、Xopsymlは、それぞれ、JSONやYAMLといった深い階層構造を持つデータであり、複数可変参照の抽出といった、通常はランタイムで行われる処理を、静的なポインタチェーンや構造ルーティングへ変換するためのツールです。

これらは「動的探索を静的構造へ置換する」という原理を、データ操作の領域に適用したものです。

### Structural Diagnostics（RZAF）

RZAFは、コードをテキストやASTとしてではなく、純粋な構造トポロジーとして扱う静的解析機です。
ロジックの脆弱性や状態遷移を、構造空間としてのコードから直接抽出するための仕組みであり、解析という領域において「動的検証を静的構造へ置換する」という原理を適用しています。

現在は、RZAFをさらに発展させて、RZAFと同じ構造を保ちながらRustの完全なASTを構築するツールも作成中です。

これらのCrateは、扱う領域や抽象度が異なりながらも、すべてが「動的計算を構造へと変換する」という同じ命題が、実際のシステムレイヤで成立することを示しています。


## 5. 構造計算モデルの可能性

Cognitive OS の着想から始まったこの取り組みは、気づけば十数個の Crate を形にするプロジェクトへと広がりました。これらの成果は単なる実装の積み重ねではなく、すべてgaが「動的計算をコンパイル時の静的トポロジーへ置換する」という同じ構造的発想から生まれています。

この統一性は偶然ではありません。Rust が持つ安全性と制約のトレードオフを、構造の再解釈によってバイパスできるのではないかという発想があり、その結果として、より広い領域で扱える計算モデルが形成されていきました。たとえばOrdexをArena Allocatorとして導入すれば、複数要素への同時可変参照という制約が構造的に解消され、16要素までは`O(1)`、それ以上の要素に対しても`O(NlogN)`で扱えるようになります。これは非線形構造を扱ううえで、ひとつの有力な基盤になり得ます。

ベンチマークやスコアとして現れている速さは、こうした構造の変化がもたらした結果にすぎません。ランタイムで発生していた無駄な計算をコンパイル時へ転嫁し、それでもコンパイル時の負荷が許容できるのであれば、ランタイムにより多くの処理を詰め込むことができます。そして、この発想は Rustに限った話でもありません。

構造やトポロジーの最適化が、計算の新しい表現形式として認知されれば幸いです。
