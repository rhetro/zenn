過去の3つの投稿では、まず「動的計算の静的トポロジーへの還元」について、そしてその実装例として2つの独自クレートである[Axioma](https://github.com/rhetro/axioma)と[Zan-sort](https://github.com/rhetro/zan-sort)を挙げ、具体的な構造的アプローチについて記述しました。

Rustの標準ライブラリに採用されているソートや、一般的に導入されているクレートは、あらゆる環境に適応できるソフトウェア的な「汎用性」を保証しています。

しかし、この汎用性という抽象レイヤは、ハードウェア最適化が要求する空間コスト・構造的制約・環境依存性といった代償を許容しないため、物理トポロジーとの整合性は設計段階で削ぎ落とされます。

汎用性を優先する設計では、データ配置や評価順序を特定のキャッシュライン幅や帯域構造に合わせて再構成することができません。どの環境でも破綻なく動作することを保証するために、計算モデルは人間にとって直感的な論理構造（AoS・抽象レイヤ）を保持し続け、物理トポロジーへの同期は構造的に成立しなくなります。

計算をアルゴリズムではなく構造として扱うと、評価過程は人間の論理構造ではなく、ハードウェアの物理トポロジーへ直接マッピング（写像）されます。

前回のZan-sortの記事で取り上げたような、比較の削減やキャッシュラインへの整列といった “高速化テクニック” として語られる操作は、構造化された計算においては、物理トポロジーへの適合結果として現れたものです。

Rustという安全性中心の言語であっても、計算を構造化することで、物理トポロジーとの整合性が構造レベルで成立します。

## 「トポロジー」という言葉と6段階の抽象化

過去の記事では「静的トポロジー」、「トポロジー空間」、「トポロジーへの投影」などという言葉を用いてきましたが、これは数学的なトポロジーではなく、「構造的配置（マッピング）」という意味で使用しています。

この一連の記事における「物理トポロジー」とは、CPUキャッシュ階層・キャッシュライン幅・DRAM帯域・NUMA配置など、シリコン上に物理的に確定している「空間構造」そのものを指します。

計算をトポロジー的に変換することで何が変わるのかについて、一段階ずつ抽象化していくと以下のような構造レイヤーとして定義されます。

① 「高速化のテクニック」  
→ ② 「設計原則としての説明」  
→ ③ 「ハードウェア整合性」  
→ ④ 「ランタイムの消滅」  
→ ⑤ 「動的計算の静的化」  
→ ⑥ 「計算＝構造的決定論」  

例えば、[前回の記事](https://zenn.dev/rhetro/articles/zan-sort)の`Zan-sort`では、次のような対応付けが行われています。

### Zan-sort：6段階抽象化対応表（一覧）

| 抽象レイヤー | `Zan-sort`における対応内容 |
|---------|-----------------------------|
| **① 高速化のテクニック** | 比較削減・キャッシュ効率・並列scatter |
| **② 設計原則としての説明** | 動的計算の排除・幾何構造化 |
| **③ ハードウェア整合性** | DRAM帯域飽和・キャッシュ階層整合 |
| **④ ランタイムの消滅** | 比較・同期・調停のゼロ化 |
| **⑤ 動的計算の静的化** | Prefix-sumによる静的トポロジー |
| **⑥ 計算＝構造的決定論** | 計算＝幾何構造の物理的適用 |

## 物理トポロジーとしてのハードウェアと「必然」

上記の6つのレイヤーの抽象化が示す通り、ここでの実装は「いかにアルゴリズムを速くするか」という①の次元の話ではありません。

計算のパラダイムを「時間的な処理」から「空間的な配置（⑥）」へと完全に移行させるアプローチです。

この視点に立つとき、CPUのキャッシュ階層（L1/L2/L3）、64バイトのキャッシュライン、そしてDRAM帯域といった要素は、単なるマシンのスペックではなく、データを配置するための「物理的なトポロジー空間」として機能します。

現代の最適化手法として語られる「AoSからSoAへの変換」や「Zero-Allocation」といったアプローチは、それ自体が独立した最適化テクニックではありません。

これらは動的計算を物理トポロジーへと静的に投影（マッピング）した結果生じる、「物理的な適合（ハードウェア整合性）」です。

スループットの向上（高速化）は目的ではなく、計算を幾何構造へ還元した結果として現れる構造的帰結です。

### 1. 論理構造（AoS）から物理トポロジー（SoA）への幾何学的再配置

AoSからSoAへの転換は、「人間の可読性」と「メモリアクセス効率」のトレードオフという具体的な事象を起点として現れます。

Rustにおいて、関連するデータを`struct`にまとめ`Vec`で保持するAoS（Array of Structs）は、人間にとって最も直感的な論理構造です。一方で、CPUのキャッシュラインや帯域幅といった物理トポロジーの観点からは、データを属性ごとに分離するSoA（Structure of Arrays）の方が高いアクセス効率を示します。

この具体的なトレードオフを抽象化すると、AoSは「人間の論理構造」であり、SoAは「ハードウェアの物理トポロジーへの幾何学的再配置」として定義されます。

つまり、SoAへの解体は単なる最適化のテクニックではありません。可読性を優先した人間の論理構造を排し、計算がシリコン上の物理トポロジーへと直接マッピングされる構造転換です。データは評価に必要な空間のみに敷き詰められ、計算は物理構造に対する決定論的なルーティングへと還元されます。

### 2. Hot PathとCold Pathの幾何学的分離

実行時に高頻度で評価されるデータ（Hot Path / キーや判定フラグなど）と、限定された回数しか呼ばれないデータ（Cold Path / 巨大なペイロードなど）は、メモリ空間上で分離しておくことでデータへのアクセス効率を改善できます。

CPUのキャッシュライン（通常64バイト）という物理境界は、ランタイム時に高頻度で使われるデータが一度に読み込まれる範囲を示しており、メモリアラインメントの予測やキャッシュミスの発生を物理的に抑制します。

人間の論理構造をハードウェアの物理トポロジーへと幾何学的に再配置する行為としてのAoSからSoAへの転換は、データ効率の最適化だけに留まりません。

データは評価に必要な空間のみに敷き詰められ、計算は物理構造に対するルーティング（③）へと再定義されます。

Hot PathとCold Pathを混在させたデータ構造は、ポインタを追跡するたびに不要なデータを読み込み、キャッシュミスを引き起こします。

計算空間を幾何学的に分離し、Hot Pathのみを独立したトポロジーとして扱うことで、動的なキャッシュミスによるランタイムコストは構造的に消去されます（④）。

### 3. 時間的調停から空間的分離（Workspace）への置換

ホットループ内でヒープ割り当て（`Vec`や`Box`の生成など）を行うことは、OSのメモリアロケータに対するロックや同期といった「時間的な調停」を発生させます。

これを避けるために固定長のアリーナやバッファ（Workspace）をあらかじめ割り当てるアプローチは、単なるヒープ割り当ての回避（Zero-Allocation）ではありません。アロケータが要求する「時間的調停」という動的計算を、事前に確保された「空間的分離（Disjoint Topology）」へと置換する構造操作です。

メモリを「動的に確保する時間軸のイベント」から「静的に固定された座標空間」へと変換する（⑤）ことで、計算そのものを事前構造へのルーティング（⑥）へと還元します。

## 構造によるRustの制約突破とコンパイラ・パイプライン

計算を「アルゴリズム」ではなく「空間への投影」として再定義すると、Rustという言語が抱える厳格な制約に対するアプローチも根本から変わります。

Rustの借用チェッカー（Borrow Checker）やスレッド間の同期調停は、基本的に「時間軸上での状態変化（動的計算）」を安全に管理するために存在しています。しかし、データを事前に決定された幾何構造へとマッピングし、完全に素（Disjoint）な空間として物理的に分離してしまえば、実行時における時間的な競合そのものが構造的に発生しなくなります。

つまり、Rustの安全性の文化を破壊するのではなく、実行時の検証や調停といった「動的計算」を、コンパイル時や構造設計の段階でトポロジー的に消去できます。

この「動的計算の静的消去」がもたらす構造的メリットは、Rustコンパイラがコードを解析し、機械語へと変換していくパイプラインにおいて確認できます。

1. **AST（抽象構文木）とマクロ展開**  
   `macro_rules!`などのマクロは、コンパイルの極めて初期段階で展開されます。この時点では「型（Type）」の情報は存在せず、純粋な構文（Syntax）の変形のみが行われます。Axiomaのような静的構造の投影は、この段階で実行されます。
2. **HIR（高レベル中間表現）による型解決**  
   ASTから変換されたHIRの段階で、初めて型推論やトレイトの解決が行われます。
3. **MIR（中レベル中間表現）と借用チェック**  
   Rustの特徴である「複数可変参照の禁止（エイリアシング規則）」と「ライフタイムの検証」は、このMIRの段階で静的に検証されます。ここにおいて、データがメモリ上で競合していないことが厳密に証明されます。
4. **LLVM IRとハードウェア最適化**  
   MIRで可変参照の単一性（エイリアシング規則）とライフタイムが検証されたコードは、LLVM IRへと変換されます。Rustコンパイラはこの検証結果に基づき、参照（特に`&mut`）に対してLLVMの`noalias`属性（ポインタが指すメモリ領域が重複しない保証）を付与します。LLVMはこのエイリアス非存在の保証を基に、ポインタのエイリアスチェックを省略し、SIMD化（自動ベクトル化）やメモリアクセスの並び替えといった低レイヤのハードウェア最適化を適用します。

もし、データの構造や参照関係を実行時（ランタイム）の動的計算に依存してしまうと、MIRはコンパイル時に静的な安全性を証明できません。その結果、LLVMは境界チェックや安全装置を残した保守的なコードを生成せざるを得ず、ハードウェア最適化の適用範囲が限定されます。

設計段階でデータを「素な空間（Disjoint Topology）」として完全に分離しておくことは、コンパイラのASTからMIRに至るパイプラインにおいて「動的計算の余地」を排除することを意味します。コンパイラとLLVMが要求する静的トポロジーをコードの構造そのもので証明することで、ランタイムのオーバーヘッドは構造的に消滅します。

## 構造的最適化が要求する代償と射影系列

Rustの標準ライブラリや汎用クレートは、あらゆる環境・データ分布に対して破綻なく動作することを前提に設計されています。計算を物理トポロジーへ同期させる構造的最適化は、この前提と構造的に衝突します。

物理境界（キャッシュライン・DRAM帯域）への過剰適合は、以下の代償を伴います。

* **空間コストの増大**  
  時間的調停（動的割り当て・ロック）を排除するため、事前割り当てによる空間消費を許容する必要があります。
* **可読性とメンテナンス性の低下**  
  AoSや抽象レイヤを保持できず、SoAなどの幾何学的配置を強制するため、コードは低レイヤ・フラット構造へ収束します。ソースコード上の論理的可読性は低下します。
* **汎用性の喪失と実行環境の限定**  
  物理トポロジーへの同期は特定のスケールで高い性能を発揮しますが、用途・環境の汎用性は低下します。適用可能なデータ分布やアーキテクチャは限定されます。

これらの代償を引き受けたこれまでのCrate群は、動的計算を構造へ還元するという単一原理を、異なる領域へ適用した系列です。

* **Axioma**：階層構造を静的空間へ投影し、パースを構造的に消去します。
* **Zan-sort**：順序付けを幾何空間へ投影し、比較を構造的に消去します。

既存の汎用アーキテクチャにおいてこれらは制約となりますが、Axiomaを基盤とした構造的アーキテクチャにおいては、物理トポロジーへ同期するための構造コストとして再解釈されます。
