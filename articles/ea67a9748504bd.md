**Axioma**というCrateをつくった動機は、RustにおけるJSONの扱いが煩雑であるという理由からです。

一般的なプログラムにおいて、動的にJSONをパースし処理する必要性は多く存在します。

外部APIから送られてくるデータやユーザーからの入力データが固定のスキーマでないことはよくあり、それらに対しては動的に判定して処理する必要があるからです。

膨大なJSONに対しては、ストリーミングパースが一般的であるし、設定ファイルなどは頻繁に編集される可能性もあります。

一方で、不安定なJSONに対応するために、わざわざRustのメリットである安全性や高速性を犠牲にするのは本末転倒です。

JSONは前処理されていたほうが圧倒的に扱いやすいし、前処理されているのであれば、本当に必要な分だけを適切に扱えれば良い。

その前提に立つと、動的にJSONをパースし、実行時に構造を探索するという計算モデルは、階層構造を持つJSONのようなデータに対して必ず一定のランタイムコストを発生させます。

構造が事前に決定している領域においては、これらの動的計算は本質的に不要であり、階層構造を静的なトポロジー空間へ投影することで、ランタイムにおける検索・判定・分岐といった処理を完全に消去することが可能になります。

**Axioma**および**Axiomabuf**は、この静的投影モデルをJSONおよびProtobufへ適用した実装であり、階層構造を持つデータに対する動的計算を構造的に消去するための手段として位置づけられます。


## 1. ランタイムパースにおけるオーバーヘッドの構造

Rustにおける外部データの扱いは、「データ構造を実行時にパースしなければならない」という前提が暗黙の了解として存在しています。

RustでJSONを扱う際、通常は `serde_json::Value` を用いて木構造を構築し、文字列パスを辿りながら値を探索するか、`#[derive(Deserialize)]` を用いてStructへマッピングします。

動的なデータを処理する場合には、これらは非常に合理的な手法に見えますが、内部では以下の「動的計算（Dynamic Computation）」が必須のランタイムコストとして発生しています。

- 文字列パスの動的解析・探索
- 木構造の動的トラバーサル（ポインタ追跡）
- 実行時の型判定および分岐評価
- `Vec` や `HashMap` の連続的なヒープ割り当て
- ポインタ追跡に伴うキャッシュミス

しかし、動的に処理しなければならないという前提を取り払えば、動的計算は構造とトポロジーの設計によってコンパイル時に静的に消去することが可能になります。

扱うデータ構造が事前に決定しているならば、その構造をコンパイル時に座標空間へ投影（Static Projection）すれば、必須だと思われていたランタイムコストは不要になります。


## 2. JSONを2D Grid（（x, y）座標）へマッピングする

Tree Diagram（木構造）であるJSONなどのデータ構造を、2Dの(x, y)座標へそのままマッピングするとどうなるか。

これが最初の発想でした。

木構造の探索は、階層の深さと幅に依存する複合的な動的計算であり、構造が大きくなるほど探索コストが増大しますが、この2Dマッピングによる静的な座標空間へ投影は、この探索そのものを O(1) の固定アクセスへと還元することができます。

Axiomaによる2Dマッピングを以下のJSONを例に挙げます。

```json
{
  "users": [
    {"id": 1, "name": "A"},
    {"id": 2, "name": "B"}
  ]
}
```

通常は `"users"` から配列、インデックス、`"name"` と順次追跡しますが、事前に決定されたトポロジーにおいては、各ノードを決定論的な2D座標 `(Row, Col)` へ直接マッピングすることができます。

Axiomaでは、以下の変換規則（Topology Physics）に従って階層を疎（Sparse）構造の座標空間へマッピングします。

| 構造 | 投影ロジック | 座標変換 |
| :--- | :--- | :--- |
| **Object** `{ K: V }` | **Vertical Drop**（Keyの位置を維持し、Valueを直下に配置） | `Key: (r, c)` <br> `Val: (r+1, c)` |
| **Array** `[ A, B ]` | **Horizontal Spread**（横方向へ展開する透過コンテナ） | `A: (r, c)` <br> `B: (r, c + width(A))` |
| **Empty** `{}`, `[]` | **Void Consumption**（空間として1列を消費） | `(r, c) -> Null` |
| **Leaf** `Value` | **Materialization**（値の実体化） | `(r, c) -> AxiValue` |

配列を水平方向へ展開することで全要素の完全アドレス可能性（Total Addressability）を保証し、階層構造を直交する2D行列（Matrix Topology）へ落とし込みます。

```text
Row 0: .users[0].id   -> (0, 0)  Offset 0x00
Row 1: .users[0].name -> (0, 1)  Offset 0x08
Row 2: .users[1].id   -> (0, 2)  Offset 0x10
Row 3: .users[1].name -> (0, 3)  Offset 0x18
```

この「階層から座標空間への変換」をコンパイル時に完了させるのが、Axiomaの役割です。


## 3. `macro_rules!` による構造計算の実装

Axiomaは `proc-macro` を使用せず、`syn` や `quote` によるAST生成も行いません。外部依存を持たない純粋な `macro_rules!` のみで構築しています。

AST（抽象構文木）は構造を構造として扱うことが困難であるためです。

`proc-macro` はトークンからASTへの変換過程で膨大な中間生成物を生み出します。構文木へ抽象化されることで生のトークンが持つ空間的配置（トポロジー）は隠蔽され、ASTの構築および解析自体がコンパイル時間の増大を招きます。

対して `macro_rules!` はASTを介さず、生のトークン列（Raw Token Stream）を扱います。トークン列そのものを構造空間（Topology）として直接評価できるため、1-passで座標空間への投影が可能になります。

Axioma内部では、このトークン空間における数え上げによって物理座標を決定するマクロ `__axi_calc!` が機能しています。

```rust
#[macro_export]
#[doc(hidden)]
macro_rules! __axi_calc {
    ( [ MAX ] ) => { usize::MAX };
    ( [ ] ) => { 0usize };
    ( [ $($tok:tt)+ ] ) => {
        [ $( $crate::__axi_unit!($tok) ),* ].len()
    };
}
```

このマクロは、受け取ったトークン列を評価コストなしにユニット配列へ変換し、その長さを取得します。「トークン列の累積数え上げ＝空間の物理座標」という写像をコンパイル時に成立させています。

また、宣言的マクロの再帰制約を回避するため、CPS（Continuation-Passing Style）パターンを導入しています。

マクロの処理結果とともに「次に呼び出すべきマクロと文脈（Callback）」を引数として引き渡すことで、深いネスト構造を安全に展開します。

```rust
macro_rules! __axi_walk {
    ({ $($content:tt)* }, [ $($r:tt)* ], [ $($c:tt)* ], $lk:expr, $b:tt, $cb:tt) => {
        $crate::__axi_obj!({ $($content)* }, [ $($r)* ], [ $($c)* ], $b, $cb)
    };
    // ...
}
```

この「宣言的マクロとCPSによるコンパイル時構造展開」は、S式計算エンジンである Emlex とも共通する構造計算モデルです。自作のツール群は独立したユーティリティではなく、すべて同一の計算思想に基づいています。

必要となるのはクレート根幹での `#![recursion_limit = "1024"]` の宣言のみであり、`macro_rules!` は完全なコンパイル時構造計算機として機能します。


## 4. Axiomaの3つの投影エンジン

Axiomaは、データ規模や目的に応じてコンパイル時間、構造復元性、バイナリサイズのトレードオフを最適化する3つの投影エンジンを提供します。

- **`kotowari!`**：構造復元性を削ぎ落とし、最小のコード生成量と最速の`O(1)`アクセスを実現する小〜中規模向け値検索エンジン。
- **`axioma!`**：ノード種別とスキップ幅を保持し、トポロジー構造の完全な保存と`O(1)`アクセスを両立する完全保存エンジン。
- **`imprint!`**：データを静的配列へ追い出すことでバイナリのコード膨張（Binary Bloat）とコンパイル時間の激増を防ぎ、大規模データに対応するデータ領域埋め込み型エンジン。

### 1. `kotowari!`（The Lossy Flash Engine）

`kotowari!`は、値検索に特化したエンジンです。構造の復元可能性（NodeKind）を削ぎ落とし、座標 `(Row, Col)` から値（`AxiValue`）へのマッピングのみを行います。

```rust
use axioma::prelude::*;

let matrix = kotowari!({
    "server": { "host": "localhost", "port": 8080 }
});

let port = matrix(1, 0); // AxiValue::Num("8080")
```

### 2. `axioma!`（The Lossless Flash Engine）

`axioma!`は、完全なトポロジー保存エンジンです。値に加え、以下のトポロジー符号（NodeKind）とスキップオフセット（`next_c`）を返します。

| 符号 (`u8`) | 種別 | 空間的機能 |
| :---: | :--- | :--- |
| `1` | `ObjKey` | Objectのキー。直下 `(r+1, c)` にValueを持つ |
| `2` | `ObjValue` | Objectの値（スカラー葉ノード） |
| `3` | `ArrayItem` | Array要素。水平方向（`c` 軸）に連続展開 |
| `4` | `EmptyObj` | 空オブジェクト `{}`。1列を消費して終端 |
| `5` | `EmptyArray` | 空配列 `[]`。1列を消費して終端 |
| `0` | `Null` | 空間外（Out of bounds）または無効セル |

```rust
let matrix = axioma!({
    "huge_payload": { /* ... 巨大な構造 ... */ },
    "target": "found"
});

let (kind, next_c, val) = matrix(0, 0);

// next_c（兄弟オフセット）を使用し、huge_payload 全体を`O(1)`で移動
let (_, _, target) = matrix(0, next_c); // AxiValue::Str("target")
```

### 3. `imprint!`（The Drive Engine）

`kotowari!` や `axioma!` は巨大なJSONに対してインラインの判定分岐を大量発生させるため、バイナリサイズ（Text Segment）の肥大化とコンパイル時間の増大を招きます。

`imprint!` はコンパイル時にCPSを用いてスキップリストを計算し、全トポロジーをデータ領域（`.rodata`）上の固定配列 `&[(row, col, skip, width, thunk)]` へ追い出します。

これにより、命令列の肥大化を防止し、大規模な構造に対してもコンパイル時間を低く抑えることができます。

実行時は、以下の階層スキップ探索（Hierarchical Skip Search）によって要素を特定します。

```rust
let mut __axi_idx = 0;
while __axi_idx < __AXI_TABLE.len() {
    let (__axi_r, __axi_c, __axi_skip, __axi_width, __axi_thunk) = __AXI_TABLE[__axi_idx];

    if __axi_r == __axi_row && __axi_c == __axi_col {
        return __axi_thunk();
    }

    if __axi_row > __axi_r && __axi_col >= __axi_c && __axi_col < __axi_c + __axi_width {
        __axi_idx += 1; // サブツリー内部へ降下
    } else {
        __axi_idx += __axi_skip + 1; // サブツリー全体を一括スキップ
    }
}
```

この幾何判定によりサブツリーを直ちに跳び越え、Text Segmentを膨らませることなく `O(log N)` で巨大データを走査できます。


## 5. 静的ポインタチェーンによる探索の消滅

通常のJSONアクセス（`serde_json::Value`）は、実行時に文字列キーのハッシュ検索、配列のインデックス走査、再度のキー検索といった手順を順次実行します。

一方、Axiomaのアクセスは、マクロ展開によって単一の `match (row, col)` パターンへ直接還元されます。

```rust
move |__axi_row: usize, __axi_col: usize| -> (u8, usize, AxiValue) {
    match (__axi_row, __axi_col) {
        (0, 0) => (1u8, 2usize, AxiValue::Str("server")),
        (1, 0) => (2u8, 2usize, AxiValue::Str("localhost")),
        (0, 2) => (1u8, 4usize, AxiValue::Str("target")),
        (1, 2) => (2u8, 4usize, AxiValue::Str("found")),
        _ => (0u8, usize::MAX, AxiValue::Null),
    }
}
```

コンパイル時にパスが直交座標へ還元されているため、実行時の探索ループおよび動的分岐は機械語レベルで存在しません。

実行時に残るのは、固定アドレス（ジャンプテーブル）への単なる直接アクセスのみとなります。


## 6. ランタイム計算の完全消去と実測値

119個の構造ノード（325セルに展開されるSparse Grid）を含むJSONペイロードに対する実測値は以下の通りです。

| エンジン | コンパイル時間（AST展開） | 実行時レイテンシ（最深部アクセス） | 計算量 | 配置セグメント |
| :--- | :--- | :--- | :--- | :--- |
| **`kotowari!`** | ~92 ms | 43.8 ns | `O(1)` | Text Segment |
| **`axioma!`** | ~515 ms | 44.0 ns | `O(1)` | Text Segment |
| **`imprint!`** | ~144 ms | 93.2 ns | `O(\log N)` | Data Segment |

`axioma!`（Lossless）と `kotowari!`（Lossy）の実行時レイテンシはともに sub-50ns（~44ns）です。

`axioma!` が返す `(NodeKind, next_c, AxiValue)` のタプル構造オーバーヘッドはLLVMのインライン化によって消去され、アクセスコストのみが残ります。

これは処理の高速化ではなく、パースという計算そのものをコンパイル時に消去した結果です。


## 7. Static Projection（静的投影）

Axiomaは、「動的計算の静的トポロジーへの還元」という中心命題をデータ表現の領域へ適用した具体化（Static Projection）です。

Opejson、Xopsyの次に作られたCrateで、構造においてJSONをよりPrimitiveに扱えるようにするために作成しました。

`kotowari!`や`axioma!`を使いこなすためには、現状でも、制限された環境や限られたリソースの中で有用であるはずです。

一方で、これらを真に使いこなすには、JSONをシステムの根幹に据えて、「コンパイル」という概念を根本から考え直す全く新しいアーキテクチャの可能性を示唆しています。

Axiomaは、計算モデルを再構築する新しいパラダイムの起点として位置づけられます。
