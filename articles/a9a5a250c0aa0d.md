`Ordex`は「複数要素への同時可変参照（Aliasing Rule）」の問題を、実行時の排他ロックではなく「空間的非重複性（Disjoint Topology）」の確定によって解決するように設計されたアリーナアロケーターです。

[前回の記事に書いたPredator & Prey Boidsシミュレーション（3,500体規模）]()では、非線形な相互作用を `clear_and_verify` による内部バッファの循環利用（メインループ内ゼロアロケーション）かつ高フレームレートで計算されている挙動を可視化しました。

今回は、非連続インデックス群が16-slot Chunk空間へ再整列される内部メカニズム（アリーナ構造、`VerifiedIndices`によるバケットルーティング、`OrdexIter`によるバッチ更新）を可視化するデモツール **『Ordex Topological Visualizer Demo』** のアーキテクチャと実装について解説します。

## 1. 原点：空間トポロジーによる借用調停

エイリアシングの安全性は、アクセス毎の実行時監視（時間）ではなく、メモリ空間の非重複な配置構造（トポロジー）によって確定します。

グラフ構造やECSなどの非線形データ構造において、離散した複数要素への同時可変アクセスは不可欠です。

従来の`RefCell`や`Mutex`による状態追跡は、アクセス毎に動的チェックを挟むため、CPUの分岐予測阻害やキャッシュミスを引き起こす可能性があります。

```rust
// 従来：アクセス毎に実行時状態をチェックする（時間的調停）
let mut node_a = arena[idx_a].borrow_mut();
// もし偶然 idx_a == idx_b だった場合、以下の行でランタイムパニック（クラッシュ）が発生する
let mut node_b = arena[idx_b].borrow_mut();
```

一方で、Ordexはアクセス実行前にインデックスの非重複性を空間構造として確定させます。

```rust
// Ordex：アクセス前にインデックスの非重複性を空間構造として確定させる
let verified = VerifiedIndices::new(vec![idx_a, idx_b]);

arena.ordex(&verified, |mut iter| {
    while let Some(node) = iter.next() {
        // 同時書き換え
    }
});
```

* **静的アライメント (`align!`, $N \le 16$)**: 
  スタック上のアンロール比較（$O(N^2)$）をレジスタ内で完結させ、DRAMフェッチ待ち時間の裏側で検証を終了させます。
* **動的バケットルーティング (`ordex`, $N > 16$)**: 
  64バイトアライメントされたSoA配置のワークスペースを用い、算術スケーリングとビットマップ演算により償却 $O(N)$ で非重複空間へ還元します。

このDemoでは、この空間構造への還元プロセスをWASM環境下で可視化します。

## 2. Ordex Topological Visualizerのアーキテクチャ：Dual-Aspect Engine

このDemoでは単一の`OrdexArena`を「論理座標（Graph）」と「物理配置（Topology）」の二相から同時に可視化しています。

* **Graph Domain（論理空間・左）**:
  2D座標上に位置する50,000個のNode群です。空間ハッシュやドラッグ選択によって抽出される不連続（Sparse）インデックス集合です。
* **Topology Domain（物理空間・右）**:
  Ordex内部ワークスペースの500 Chunks（計 8,000 スロット）です。`VerifiedIndices`によりエイリアシングが排除され、64バイト（L1キャッシュライン）アライメントに適合する16-slot単位で整列された物理メモリ配置です。
  ※ $16 \text{ slots} \times 500 \text{ chunks} = 8,000 \text{ slots}$

### WASM生メモリ直結による描画

50,000件のノードと8,000件の整列スロットを描画するため、WASM/JS間の**JSONシリアライズや配列コピーは行っていません**。

Rust側の`VisualizerCore`はバッファの先頭ポインタ（`positions_ptr`,`raw_indices_ptr`）をそのまま返却します。

```rust
#[inline]
pub fn positions_ptr(&self) -> *const f32 {
    self.positions.as_ptr()
}

#[inline]
pub fn raw_indices_ptr(&self) -> *const u32 {
    self.raw_indices_cache.as_ptr()
}
```

JS側は`wasm.memory.buffer`から直接`Float32Array`および`Uint32Array`ビューを生成し、Canvasへ描画します。

## 3. 実行3フェーズ（Sprout / Harvest / Resonate）

Ordex Topological Visualizerの操作体系はOrdexのライフサイクルに対応します。

### STEP 01 — Sprout (Arena Allocation)
WASM線形メモリ内に 50,000個の`Node`構造体を確保します。Generational Indexテーブルとフリーリストを初期化し、世代管理を完了します。

### STEP 02 — Harvest (SoA Routing & Verification)
ドラッグ選択等により不連続な8,000個のノードを抽出します。
`VerifiedIndices::clear_and_verify`は内部ワークスペースバッファをクリアして再利用するため、追加のヒープ割り当て（Zero-Allocation）を行わずに、不連続インデックス群を右パネルの500 Chunks（8,000 スロット）へ100.0% の密度で即座に再整列します。

### STEP 03 — Resonate (OrdexIter Physics)
`OrdexIter`により、毎フレーム追加のヒープ割り当てを発生させずにバッチ一括更新を実行します。選択された8,000ノードの物理座標がWASM内部で直接書き換わります。

## 4. Resonateにおける検証済み集合への動的追従と安全境界

`Resonate`は`VerifiedIndices`によってaliasingが排除された集合に対してのみ動作するため、どれだけ高速に動いても安全性が崩壊することはありません。

Resonate動作中にドラッグ範囲を変更すると、新たに選択された領域のノード群のみが即座に物理変調を受け、それ以前の選択領域は即座に静止します。

### 処理フロー

1. JS側が選択範囲内のraw indexを集約します。
2. WASM側`engine.set_selection()`へ渡し、Rust内部で`workspace.clear_and_verify()`を実行します。
3. 非重複な`VerifiedIndices`空間を事前確保バッファの循環利用（Zero-Allocation）で再構築します。
4. 毎フレーム実行される`OrdexIter`の参照対象が新しい検証済み集合へ切り替わります。

```rust
pub fn execute_batch_mutation<F>(&mut self, mut mutator: F)
where
    F: FnMut(&mut Node),
{
    self.arena.ordex(&self.workspace, |mut iter| {
        while let Some(node) = iter.next() {
            mutator(node);
        }
    });
}
```

`OrdexIter`で`Node`の状態を更新し、その結果を公開用SoAバッファへ同期する二段階構成をとることで、メモリ安全性を保持したまま 描画ループに同期したリアルタイムの物理演算を行います。

## 5. 双方向（Dual-Domain）インスペクション

Graph Domain（論理）と Topology Domain（物理）の対応関係を双方向に特定する機能も追加しました。

* **Graph Domain（左）のノードをホバー**:
  カーソル位置のノードに対応する右パネル（Topology Domain）の`Chunk ID`および`Slot Offset`（例:`Index #11857 -> Chunk 411 [Offset 12]`）を強調表示。
* **Topology Domain（右）のスロットをホバー**:
  右パネルの任意のChunk/Slotに対応する左パネル上のノード位置を特定表示。

視覚上のオブジェクトがメモリ空間（L1キャッシュライン/SoAバケット）のどの領域に配置されているかが確認できます。

## 6. Ordexがもたらすトポロジー還元の意味

Ordexによるエイリアシング解決の検証過程は以下の3段階で構成されています。　

1. **理論**: エイリアシング問題を時間的調停から空間トポロジー確定へ還元。
2. **実用**: Predator & Prey Boidsシミュレーションによるスループット検証。
3. **可視化**: WASM生メモリとSoA再構築プロセスを直結・可視化する 『Ordex Topological Visualizer』。

動的処理の前提を検証済みの空間構造へ再配置するモデルは、ECS、GUI、グラフィックエンジンなど、多体相互作用を扱う非線形構造全般の基盤として機能します。
